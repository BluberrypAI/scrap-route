# 업체 사진 검토의 긴 응답과 부분 실패 보강

## 바꾼 이유

2026-11-16 실제 PP 연구 사진 시험에서 업체 3곳의 공개 근거와 물량 질문을 한 응답으로 만들 때 두 차례 시간 초과가 났다. 같은 두 사진으로 후보 2곳씩 검토한 7요청은 응답했지만, 약 62~76초가 걸렸다. 성공한 작은 묶음만으로 전체 후보 검토가 안정적이라고 결론 내리지 않았다.

## 동작

1. API의 후보 상한은 5곳으로 유지한다. 같은 후보 키를 두 번 보내면 422로 거절한다.
2. 사진이 있으면 업체·설명을 보여주지 않고 관찰을 한 번만 한다.
3. 물량 검토를 **업체당 한 호출**로 나누고, 요청당 최대 3개 비교를 동시에 실행한다. 모든 비교에 같은 관찰을 전달한다. server는 로트 후보를 최대 3곳씩 보내 사진 관찰과 비교 한 번의 대기를 HTTP 175초 범위에 맞춘다.
4. 한 업체의 시간 초과·잘못된 JSON·중복 결과는 그 업체만 미완료로 남긴다. 다른 업체의 성공 결과를 버리지 않는다. 시간 초과 후 자동 재호출하지 않는다.
5. 사진 관찰 자체가 실패하면 비교를 시작하지 않는다. 물량 없는 공개 근거 전용 요청은 기존 단일 호출을 유지한다.

HTTP 입출력 필드·엔드포인트, 후보 생성, 수락·QR·완료 계약은 바꾸지 않았다. 기존 server와 새 웹 PR #48 모두 같은 응답을 읽는다. 사진 관찰·물량 비교를 했다는 기존 분석 버전도 유지한다. 과거에 정상 완료한 검토를 무효화하는 변경은 아니다.

## 질문의 구분

- **설명 불일치**: ‘흰색 조각만 있다’는 진술과 ‘빨강·파랑 조각이 보인다’는 선명한 관찰이 직접 모순될 때.
- **세척 확인**: 얼룩이 보이지만 실제 부착물인지 모를 때.
- **시험 확인**: 재질·수분·순도 자료가 없을 때.
- 여러 색을 여러 고분자로 단정하거나, 사진만으로 세척 이력을 반박하지 않는다.

이는 프롬프트의 구분 기준이며 자연어 판정의 완전한 일관성을 보장하지 않는다. 사진이 공개 공정 근거·허가·실제 수락을 대신하지 않으며 자동 승인은 계속 false다.

## 검증 범위

자동 검사는 후보 5곳 전부 검토, 동일 사진 관찰 보존, 업체별 단독 비교·동시 3개 제한, 한 업체만 실패 격리, 중복 입력 거절, 사진 없는 물량·기존 공개 근거 호출을 확인한다.

### 후속: 조건 등록 웹 시험에서 발생한 2곳 시간초과

두 곳씩 묶던 버전에서 대운프라스틱 나주와 중일머티리얼즈 인천이 한 호출의 provider_timeout으로 함께 미완료가 됐다. 이후 업체당 한 호출로 분리하고, 같은 합성 PP 1,000kg 입력을 두 곳에 실제 Azure로 다시 보내 42.4초에 모두 응답했다. 대운은 공개 공정 근거 확인, 중일은 사출 잔재 형태 반입 근거 부족으로 남았다. 둘 다 물량 검토 응답은 완료했고 자동 승인은 false다.

이미 A→B 입고한 처리 건의 과거 검토·인계 기록을 바꾸지 않았다. 별도 재검증 결과로 저장했다. 이 시험은 사진 없이 진행했다. 아래의 사진 시험 표는 앞선 두 업체 묶음 버전에서 수행한 결과이며, 이번 단독 호출 버전의 사진 실호출 재검증으로 계산하지 않는다.

단독 호출은 응답 시간과 실패 영향 범위를 줄이기 위한 변경이지 모든 Azure 요청의 완료를 보장하지 않는다. 직접 route에 로트 후보 5개를 보내면 비교가 두 차례에 나뉘므로 사진 관찰 포함 대기가 175초를 넘을 수 있다. server와 함께 적용해 로트 요청 3개 제한을 사용한다.

- 전체 pytest: 566 passed, 72 skipped, 24 subtests passed. 생략된 검사를 통과로 계산하지 않았다.
- Ruff 검사와 수정 파일 포맷 검사 통과.
- 실제 FastAPI HTTP 요청 → Azure `resource-gpt-6-astra`, 추론 high. 모델을 가짜 응답으로 대체하지 않았다.
- 최신 server의 참조 카탈로그에서 PP 파쇄품 후보를 가져왔다. DB·계정·QR를 포함한 전체 서비스 E2E는 아니다.

4요청에서 후보별 응답 18개를 받았으며 각 요청 안의 사진 관찰은 모든 후보에 동일했다. 이는 응답 완료와 이 네 사례의 관찰 결과이며, 정확도 100% 또는 18개 업체의 반입 가능 판정이 아니다. 예를 들어 세척 확인 시험에서 5곳 중 4곳은 공개 투입 형태 근거가 부족한 상태로 유지됐다. 전부 자동 승인 false, 수신기업 확인 필요를 유지했다.

사진은 Wageningen 보고서 2030의 Figure 6.1, p.50에서 얻은 기존 세척 전·후 PP 사진이다: https://edepot.wur.nl/518299 . 세척 후 사진을 무오염 정답으로 간주하지 않았다. 상태 설명·950kg은 합성 입력이다. 원본 사진, 해시, 요청별 원문 응답과 모델 호출 시간은 작업 폴더의 `output/verification/intake-hardening-20261117/`에 분리 보관했다.

위 사진 실험 당시에는 Docker 통합 환경이 꺼져 있어 해당 네 요청을 전체 서비스 E2E로 계산하지 않았다. 이후 같은 날 별도 A·B·C 개발용 계정으로 문진 → DB 저장 → 기업 수락 → QR → 완료를 실제 웹에서 추가 확인했다. PP 직접 종료의 후보 9곳, 두 단계 경로의 A 후보 14곳·B 후보 9곳을 모두 실제 Azure로 검토했다. 기업·물량·수락·계량 근거는 합성 시험자료이며 소셜 로그인과 실물 운송은 검증 범위 밖이다. 상세 결과는 [scrap-server 통합 보고서](https://github.com/BluberrypAI/scrap-server/blob/fix/e2e-release-20261117/docs/full-login-e2e-20261117.md)에 있다.

## 남은 운영 과제

동시 호출은 HTTP 요청당 최대 3개이며 서비스 전체 Azure 할당량 제어기는 아니다. 여러 사용자의 동시 실행과 429는 별도 부하 검증이 필요하다. 한 단계가 실패해도 다른 결과를 보존할 뿐 모든 요청의 완료를 보장하지 않는다. 서버가 전체 후보를 여러 HTTP 묶음으로 순차 요청하므로 긴 요청의 작업 큐·진행률·부분 재시도는 후속 과제다.

사진·키·기업 실데이터는 이 문서나 Git에 넣지 않는다.
